# Загальні правила роботи

Правила, що зменшують типові помилки ШІ під час написання коду.

**Компроміс:** ці правила ставлять обережність вище за швидкість. Для
дрібних задач дій на власний розсуд.

## 1. Думай, перш ніж писати код

**Не припускай. Не приховуй сумнівів. Називай компроміси.**

Перед реалізацією:
- Явно називай свої припущення. Якщо не впевнений, запитай.
- Якщо задачу можна зрозуміти по-різному, наведи варіанти, а не вибирай мовчки.
- Якщо є простіший підхід, скажи про це. Заперечуй, коли це доречно.
- Якщо щось незрозуміло, зупинись. Назви, що саме незрозуміло. Запитай.

## 2. Простота понад усе

**Мінімум коду, що вирішує задачу. Нічого «на майбутнє».**

- Жодних функцій понад те, що просили.
- Жодних абстракцій для коду, який використовується один раз.
- Жодної «гнучкості» чи «налаштовуваності», про яку не просили.
- Жодної обробки помилок для неможливих сценаріїв.
- Якщо написав 200 рядків, а можна 50, перепиши.

Запитай себе: «Чи сказав би досвідчений розробник, що це переускладнено?»
Якщо так, спрости.

## 3. Точкові зміни

**Чіпай лише те, що необхідно. Прибирай лише власний безлад.**

Під час редагування існуючого коду:
- Не «покращуй» сусідній код, коментарі чи форматування.
- Не рефактор те, що не зламане.
- Дотримуйся існуючого стилю, навіть якщо ти зробив би інакше.
- Якщо помітив непов'язаний мертвий код, скажи про нього, але не видаляй.

Якщо твої зміни залишили щось невикористаним:
- Видаляй імпорти, змінні й функції, які стали непотрібними через ТВОЇ зміни.
- Не видаляй мертвий код, що був до тебе, якщо не просили.

Перевірка: кожен змінений рядок має прямо стосуватися мого запиту.

## 4. Робота на результат

**Визнач критерії успіху. Повторюй, доки не перевіриш.**

Перетворюй задачі на цілі, які можна перевірити:
- «Додай валідацію» → «Опиши, які некоректні дані вводимо і що має статися,
  потім реалізуй і перевір»
- «Виправ баг» → «Опиши кроки, що відтворюють баг, виправ, повтори кроки»
- «Рефактор X» → «Переконайся, що все працює однаково до і після»

У проєкті немає автотестів. Перевірка означає конкретні кроки в браузері
(localhost), які я можу повторити сам.

Для багатокрокових задач коротко опиши план:
```
1. [Крок] → перевірка: [що саме перевірити]
2. [Крок] → перевірка: [що саме перевірити]
3. [Крок] → перевірка: [що саме перевірити]
```

Чіткі критерії успіху дозволяють працювати самостійно. Розмиті критерії
(«зроби, щоб працювало») вимагають постійних уточнень.

**Ці правила працюють, якщо:** у змінах менше зайвого, менше переписувань
через переускладнення, а уточнювальні питання з'являються до реалізації,
а не після помилок.

# Проєкт: Щоденник тренувань (PWA)

Офлайн-щоденник для спортзалу. Використовується на iPhone як PWA
(Safari → «На початковий екран»). Дані зберігаються локально на телефоні
кожного користувача в IndexedDB. Бекенду й акаунтів немає.

Сайт: https://sevvykx.github.io/gym-diary/

## Стек
- Чистий HTML/CSS/JavaScript (ES-модулі). БЕЗ npm, збірки та фреймворків.
- Dexie лежить локально у vendor/dexie.mjs (без CDN, бо потрібен офлайн).
- Нові бібліотеки чи інструменти збірки не додавай без мого дозволу.

## Структура
- index.html: оболонка, нижня навігація, meta-теги для iOS
- css/styles.css: усі стилі
- js/app.js: хеш-роутинг (#/workout, #/history/7 ...), реєстрація Service Worker
- js/db.js: схема бази Dexie, запити, профіль, експорт/імпорт копії
- js/seed.js: стартовий список вправ
- js/utils.js: форматування дат і ваги, escapeHtml
- js/views/*.js: екрани (workout, history, exercises, records, settings,
  onboarding), кожен експортує render(container, param)
- sw.js: Service Worker, кешує файли для офлайн-режиму
- manifest.webmanifest, icons/: дані для встановлення PWA

## Схема бази (зараз db.version(2))
- exercises: { id, name, muscleGroup, isCustom }
- workouts: { id, startedAt, finishedAt|null, exerciseIds: [] }
- sets: { id, workoutId, exerciseId, weight, reps, createdAt }
- profile: один запис з id: 1 { name, goal, experience, workoutsPerWeek,
  bodyWeight|null }. Без профілю програма показує онбординг.
- Файл копії: version: 2, містить profile (об'єкт або null). Копії
  version 1 теж імпортуються, профіль при цьому не змінюється.

## Важливі правила
- Новий екран: файл у js/views/ + маршрут у routes в js/app.js.
- Новий файл у проєкті: ОБОВ'ЯЗКОВО додай його до списку FILES у sw.js,
  інакше він не працюватиме офлайн.
- Зміни схеми бази: НЕ змінюй db.version(1) і db.version(2). Додай
  db.version(3) з міграцією, щоб у користувачів не зникли дані. Онови
  version у exportAll/checkBackup, щоб старі копії імпортувалися.
- Варіанти відповідей профілю (ціль, досвід тощо) описані один раз у STEPS
  у js/views/onboarding.js. Їх використовують і вступ, і налаштування.
- Текст від користувача вставляй у HTML лише через escapeHtml().
- Інтерфейс і коментарі в коді українською.
- Дизайн: mobile-first під iPhone, темна тема, великі кнопки для однієї
  руки, safe-area відступи.

## Запуск і деплой
- Локально: python3 -m http.server 8000 → http://localhost:8000
- Деплой: push у гілку main → GitHub Pages оновлює сайт автоматично.
  Тому в main лише робочий код. Великі фічі роби в окремій гілці.
- Після кожного завершеного кроку пропонуй команду git commit з
  коротким повідомленням українською.
